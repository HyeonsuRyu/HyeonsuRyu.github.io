# 1. DB 구성 요소

DB를 인프라 관점에서 보면 크게 두 가지로 나눌 수 있다.

1. **데이터 볼륨(Data Volume)**
2. **DBMS(Database Management System)**

DBMS가 데이터를 관리하고 실제 데이터는 별도로 저장된다. 따라서 **DBMS를 어디에서 실행할 것인지**와 **데이터를 어디에 저장할 것인지**를 별도로 결정할 수 있다.

---

# 2. 데이터 볼륨 관리

데이터를 저장하는 방법은 크게 **Bind Mount**와 **Docker Volume**으로 나눌 수 있다.

## 2.1 Bind Mount

호스트의 특정 디렉터리를 컨테이너에 마운트하는 방식이다.

```text
Host
└── /data/mysql
        ↓ bind mount
Container
└── /var/lib/mysql
```

### 장점
* 데이터의 실제 위치가 명확하다.
* 백업, 디스크 교체, 스토리지 관리 등의 작업이 편리하다.
* 계층을 최소화하여 Disk I/O가 중요한 DB에서 유리하다.
### 단점
* DBMS가 컨테이너에서 실행되는 경우, UID/GID 불일치로 인한 권한 문제가 발생할 수 있다.

## 2.2 Docker Volume

Docker가 관리하는 Volume을 컨테이너에 연결하는 방식이다.

```text
Docker
└── Volume
       ↓
Container
└── /var/lib/mysql
```

### 장점
* Docker가 Volume의 생성과 연결을 관리하기 때문에 컨테이너와의 연동이 간단하다.
* Bind Mount에 비해 호스트의 특정 디렉터리와 컨테이너 내부 사용자를 직접 맞춰야 하는 상황이 줄어들기 때문에 권한 관리가 편리하다.
### 단점
* 실제 데이터가 호스트의 어디에 저장되는지 직관적으로 파악하기 어렵다.
* 데이터를 직접 관리하거나 다른 스토리지로 이전하는 작업이 Bind Mount보다 불편할 수 있다.

## 2.3 비교

| 항목        | Bind Mount    | Docker Volume |
| --------- | ------------- | ------------- |
| 데이터 위치 확인 | 쉬움            | 상대적으로 어려움     |
| 직접 데이터 관리 | 편리            | 상대적으로 불편      |
| 백업/디스크 관리 | 편리            | 상대적으로 불편      |
| Docker 연동 | 직접 설정 필요      | 편리            |
| 권한 관리     | UID/GID 고려 필요 | 상대적으로 편리      |
| 관리 주체     | 운영자가 직접 관리    | Docker가 관리    |

따라서 **데이터에 대한 직접적인 관리가 중요하다면 Bind Mount**,  
**Docker 중심의 단순한 운영과 편의성이 중요하다면 Docker Volume**을 선택할 수 있다.

# 3. DBMS 실행 환경

DBMS를 실행하는 방법도 크게 두 가지가 있다.

1. 호스트에 직접 설치
2. Docker 컨테이너에서 실행    

## 3.1 Host에 직접 설치

Ubuntu라면 APT, RHEL 계열이라면 YUM/DNF 등의 패키지 관리자를 이용해 DBMS를 직접 설치할 수 있다.

```text
Host
├── MySQL
├── PostgreSQL
└── ...
```

구성이 단순하고 운영 환경에서 관리하기 편하다는 장점이 있다.

특히 하나의 서버에서 하나의 DBMS만 운영하고, 별도의 격리가 필요하지 않다면 컨테이너를 추가하는 것보다 직접 설치하는 것이 단순할 수 있다.

반면 다음과 같은 요구사항이 생기면 관리가 복잡해질 수 있다.

- 여러 DBMS 버전을 동시에 운영
- 서비스별 격리
- DBMS별 리소스 제한
- 환경 재현
- 다른 서버로 동일한 환경 이전

## 3.2 Docker에서 실행

DBMS를 Docker 컨테이너에서 실행할 수 있다.

```text
Host
└── Docker
    └── MySQL Container
```

컨테이너를 사용하면 DBMS의 실행 환경을 호스트와 분리할 수 있다.

또한 Docker Compose 등을 이용하면 DBMS 버전과 설정을 코드로 관리할 수 있기 때문에 개발 환경을 재현하기 쉽다.

여러 버전의 DBMS를 동시에 운영하거나 다른 서비스와 실행 환경을 분리해야 하는 경우에도 유리하다.

다만 컨테이너를 사용한다고 해서 DB 운영에 필요한 문제가 사라지는 것은 아니다.

특히 다음과 같은 요소는 여전히 별도로 관리해야 한다.

- 데이터 영속성
    
- 백업
    
- 복구
    
- 권한
    
- 리소스 제한
    
- 모니터링
    
- 장애 대응
    

즉, **DB를 Docker에서 실행한다고 해서 DB 운영 자체가 Docker에 의해 해결되는 것은 아니다.**

# 4. 개발 환경과 운영 환경

DBMS 실행 방식과 데이터 저장 방식은 다음과 같이 다양하게 조합할 수 있다.

| 환경  | DBMS   | 데이터            |
| --- | ------ | -------------- |
| 개발  | Docker | Docker Volume  |
| 개발  | Docker | Bind Mount     |
| 운영  | Docker | Bind Mount     |
| 운영  | Host   | Host Directory |

각각의 목적에 따라 적절한 조합을 선택할 수 있다.

## 개발 환경

개발 환경에서는 **재현성**과 **구성의 편리성**이 중요하다.

따라서 DBMS와 데이터를 모두 Docker가 관리하도록 구성할 수 있다.

```text
Docker Compose
├── Application
└── MySQL
     └── Docker Volume
```

Docker Compose 파일만으로 동일한 DBMS 버전과 실행 환경을 쉽게 구성할 수 있고, 개발 환경을 초기화하거나 재구성하기도 쉽다.

## 운영 환경

운영 환경에서는 개발 환경보다 **데이터의 관리 가능성**이 중요하다.

따라서 DBMS는 Docker에서 실행하고, 데이터는 호스트 디렉터리에 저장하는 구성을 선택할 수 있다.

```text
Host
├── /data/mysql
│      └── DB Data
│
└── Docker
       └── MySQL
             ↑
             └── Bind Mount
```

이렇게 하면 DBMS 실행 환경은 컨테이너로 격리하면서도 실제 데이터의 위치는 운영자가 직접 관리할 수 있다.

백업이나 디스크 교체 등의 작업에서도 데이터의 위치를 명확하게 파악할 수 있다는 장점이 있다.

# 5. DBaaS

직접 DBMS를 운영하지 않고 **DBaaS(Database as a Service)**를 사용할 수도 있다.

```text
Application
     │
     ▼
   DBaaS
     │
     ▼
Managed Database
```

이 경우 DBMS 설치, 스토리지 관리, 일부 백업 및 장애 대응 등의 운영 부담을 서비스 제공자에게 이전할 수 있다.

따라서 직접 DB 인프라를 운영하는 것과 DBaaS를 사용하는 것은 단순히 "Docker vs Host"의 선택이 아니라 **운영 책임을 어디까지 가져갈 것인가**의 문제로 볼 수 있다.

다만 DBaaS를 사용하더라도 데이터베이스의 스키마, 쿼리, 권한, 백업 정책, 비용 및 장애 대응 방식 등에 대한 책임이 완전히 사라지는 것은 아니다.
